# Устройство EasyDo

## Зависимости

```text
StockFlow ──────────> EasyDo.WinForms ───> EasyDo.Core
    │                                         ▲
    └──────────────> MySqlConnector            │
                                              │
TaskBoard ─────────> EasyDo.WinForms ───────────┘
```

`Core` использует только стандартную библиотеку .NET. В нём нет ссылок на InventoryApp, WinForms, MySqlConnector, названия товаров или валюты. `WinForms` зависит только от Core и Windows Desktop Framework. Библиотека не ссылается на приложения или примеры.

## Почему отдельные блоки вместо одного класса

Один глобальный «EasyDo» быстро смешал бы запросы, интерфейс, состояние и бизнес-правила. Здесь блоки ограничены своими задачами: Store владеет соединением, Rules проверяет состояние, Flow связывает шаги, UiKit создаёт контролы. Общая композиция остаётся читаемым C# и проверяется компилятором.

Нет генерации C# в runtime, поиска методов по строковым именам, автоматической SQL-магии или service locator. Единственное выражение в таблицах — прямое свойство модели; expression используется для получения имени свойства и проверки формы выражения, а не для выполнения скрытого кода.

## Контракты

- **Flow/Rules/Sql:** неизменяемые рецепты; расширение возвращает новую копию.
- **Session:** короткое время жизни, последовательное исполнение; все созданные команды получают одну транзакцию и таймаут.
- **Store:** фабрика создаёт новое соединение на операцию; данные читателя материализуются внутри callback.
- **Async:** токены доходят до ADO.NET; rollback после отмены использует отдельный неотменённый токен.
- **UI:** только поток интерфейса; контролы и шрифты нельзя делить между потоками.
- **Layout/Grid recipes:** одноразовые; контрол принадлежит одному родителю. Matrix сначала валидирует координаты и лишь при Build меняет дерево.
- **ViewDeck:** фабрики ленивы, страницы принадлежат deck, скрытые страницы также освобождаются.
- **Ошибки:** Core не показывает диалогов. UI может показать ошибку через Safe; приложение определяет сообщение и действия.

## Как добавлять новый блок

1. Сформулируйте повторяемую задачу, например загрузку файла или расчёт заказа. Если она относится только к магазину, оставьте её в InventoryApp.
2. Передавайте зависимости через конструктор/делегаты. Не обращайтесь к статической Database из библиотеки.
3. Определите, кто владеет ресурсом, когда он закрывается и что происходит при ошибке/отмене.
4. Делайте блок обычным методом или классом C#. Специальная регистрация и изменение ядра не нужны.
5. Подключите блок через Then, FormBinding.Bind или собственный контрол в Surface/Matrix.
6. Проверьте реальную гарантию: например порядок/прерывание шагов, откат, освобождение, непересекающиеся области. Добавьте исполняемый пример в документацию.

Пример своего шага:

```csharp
static void CalculateDiscount(Order order)
{
    order.Discount = order.Total >= 10000 ? order.Total * 0.05m : 0m;
}

var recipe = Flow<Order>.Start()
    .Check(orderRules)
    .Then(CalculateDiscount)
    .Then(SaveOrder);
```

Для сложной операции состояние можно вынести в отдельный класс с промежуточными результатами. В StockFlow Checkout хранит session, корзину, заблокированные позиции и receipt. Благодаря этому порядок действий виден в одном месте, а каждый шаг можно изменить отдельно.

## Что осталось в приложении намеренно

Модели товаров, схема MySQL, правила цен и остатков, генерация демо-данных, тексты экранов, порядок меню и валюта. Перенос этих деталей в Core сделал бы его библиотекой одного магазина. Необходимая адаптация другого продукта — новые модели и сценарии, а не копирование сотен строк фабрик контролов и try/finally вокруг SQL.

## Проверки качества

В Core.Specs тестовый ADO.NET-провайдер фиксирует привязку параметров/транзакций, ошибки открытия/commit/rollback и освобождение ресурсов. StockFlow.Specs отдельно проверяет реальные WinForms-контролы и может проверить живую временную MySQL-базу. VisualParity сопоставляет оригинальную сборку и новую в изолированных AssemblyLoadContext при общих framework-контролах.

Такая проверка не заменяет тестирование конкретной новой идеи. Каждому приложению нужны собственные сценарии данных, внешних эффектов и доступа; библиотека обеспечивает только свои заявленные контракты.
