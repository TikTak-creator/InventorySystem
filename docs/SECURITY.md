# Модель защиты StockFlow 2.0

## Границы доверия

```text
WinForms / внешняя программа
        │ HTTPS + Bearer
        ▼
ASP.NET Core API: проверка сессии → роль → валидация → транзакция
        │ серверная строка подключения, TLS
        ▼
MySQL: товары, чеки, история цен, пользователи, хэши сессий
```

Приложение-клиент и входящие JSON считаются недоверенными. Наличие скрытой кнопки или корректного клиентского расчёта не даёт полномочий. Цены, себестоимость, остатки и права проверяет сервер. Это система одного магазина, без tenant-изоляции.

## Реализовано

- **Пароли:** стандартный `PasswordHasher` ASP.NET Core Identity в формате IdentityV3. PBKDF2-HMAC-SHA512, 600000 итераций, случайная соль, версия параметров в хэше. Исходные пароли в БД отсутствуют; обратимого «шифрования пароля» нет. При необходимости обновления формата хэш заменяется после успешной проверки.
- **Сессии:** 32 криптографически случайных байта (`RandomNumberGenerator`), кодирование base64url. В MySQL хранится только SHA-256 токена, ID пользователя и UTC-время истечения. Токен передаётся клиенту один раз, далее используется в Authorization. Высокоэнтропийному случайному токену не нужен медленный парольный KDF.
- **Отзыв:** каждый запрос проверяет сессию и активность пользователя в БД. Logout удаляет текущую сессию. Смена пароля и изменение активности удаляют все сессии пользователя. Подписанного токена, продолжающего работать после отключения, нет.
- **Перебор:** не более 10 запросов входа/IP/минуту и 300 запросов/IP/минуту всего на процесс. После пяти ошибок аккаунт блокируется на 15 минут; счётчик фиксируется транзакцией, а не откатывается вместе с ошибкой входа. Неизвестный пользователь также проходит проверку фиктивного хэша; для заблокированного/отключённого аккаунта возвращается общий отказ.
- **Авторизация:** роли Viewer, Operator, Admin. Удаление и управление пользователями доступны только Admin. Публичной регистрации и общего admin/admin нет. Первоначальное создание пользователей выполняет локальная серверная команда.
- **Транспорт:** API требует HTTPS, клиент проверяет доверие цепочке сертификата и имя сервера, автоматические редиректы в стандартном SDK отключены. Production-подключение к MySQL требует `SslMode=VerifyFull`. Не предусмотрен переключатель обхода TLS в рабочем приложении.
- **SQL и данные:** значения привязаны параметрами EasyDo; нет API выполнения произвольного SQL. Входные значения ограничены диапазонами, длинами и известными JSON-полями. Цена продажи считывается из БД под блокировкой, а не принимается от кассы.
- **Целостность:** чек и списание сохраняются в одной транзакции, товары блокируются в одинаковом порядке. Ключи повторов защищают POST /sales от повторной записи. При редактировании проверяется версия карточки, чтобы не перезаписать остаток устаревшим значением.
- **Конфигурация:** клиент не содержит MySQL-зависимости и строки подключения. Секреты сервера задаются средой/secret store. Поля пароля и токена не записываются в прикладные логи. Ответы запрещают кэширование; внутренние ошибки возвращают общий текст и traceId.

Минимальные длины и стоимость KDF выбраны с учётом [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Используется реализация [ASP.NET Core Identity PasswordHasher](https://source.dot.net/Microsoft.Extensions.Identity.Core/PasswordHasher.cs.html), а не собственный криптографический алгоритм. Настройка доверенных HTTPS-сертификатов описана в [Microsoft Learn](https://learn.microsoft.com/en-us/aspnet/core/security/enforcing-ssl?view=aspnetcore-8.0).

## Владение секретами

Пароль БД и закрытый ключ TLS принадлежат только серверной учётной записи. У рабочего MySQL-пользователя должны быть лишь необходимые DML-права на базу приложения; DDL и CREATE DATABASE выдаются учётной записи инициализации. Не запускайте сервер от MySQL root. Для рабочей учётной записи допустимы SELECT/INSERT/UPDATE/DELETE; миграции выполняются отдельно.

Ограничьте сетевой доступ к MySQL сервером API. Зашифруйте диски/тома и резервные копии средствами инфраструктуры; **полнотекстовое шифрование бизнес-таблиц на уровне приложения здесь не реализовано**. Сервер MySQL видит бизнес-данные для поиска и расчётов. Не следует представлять TLS и хэши паролей как шифрование всех данных на диске.

Клиент хранит пароль в поле ввода только для входа, затем очищает поле. Токен хранится в памяти процесса и отзывается при штатном закрытии с ограниченным временем ожидания. При аварийном закрытии или сетевом сбое отзыв может не пройти; сессия действует до серверного срока истечения или административного отзыва. Managed-строки не гарантируют немедленное физическое стирание из памяти; скомпрометированное устройство клиента остаётся за пределами этой защиты.

`updatedAt` в API — непрозрачная монотонная версия: при каждой записи минимум на секунду больше предыдущей, чтобы последовательные изменения внутри одной секунды различались при прежнем DATETIME-столбце. Значение может опережать часы при частых изменениях и не предназначено для аудита точного времени операции. Прямые изменения БД в обход API не поддерживают эту гарантию.

## Что требуется от развёртывания

HTTPS-сертификат с доверенной цепочкой, проверяемый TLS для MySQL, регулярные обновления .NET/MySqlConnector/MySQL/ОС, firewall, права на секреты, резервное копирование и проверка восстановления. Пример настроек — [SETUP.md](SETUP.md).

Rate limiter работает в памяти одного процесса и определяет IP по непосредственному TCP-соединению. За прокси все клиенты могут иметь один IP. Не включайте доверие произвольным X-Forwarded-For; настройте доверенные прокси и внешний лимитер отдельно. Если сервер масштабируется на несколько инстансов, блокировка аккаунтов остаётся общей в БД, IP-лимиты требуют общего внешнего слоя.

Приложение не содержит MFA, SSO/OIDC, самостоятельного восстановления пароля, сквозного шифрования, WAF, полноценного журнала финансового аудита или управления ключами резервных копий. Администратор может управлять другими администраторами; это полномочная серверная роль. Тесты не являются пентестом или сертификацией безопасности.

## Проверки

Интеграционный suite поднимает настоящий Kestrel с HTTPS и изолированную MySQL-базу. Проверяются анонимный доступ, роли, плохие пароли, блокировка, хэши, срок/отзыв сессий, неверные токены, защита версий, идемпотентность, SQL-подобный ввод и лимит входа. Отдельный отрицательный тест подтверждает, что обычный клиент отвергает тестовый самоподписанный сертификат. В тестовом транспорте разрешён только точный отпечаток временного сертификата; этот код не используется в поставке клиента.

Обнаруженные уязвимости не публикуйте вместе с действующими секретами или дампами базы. Для технического отчёта достаточно сценария воспроизведения, версии, HTTP-статуса и traceId с удалёнными паролями и токенами.
